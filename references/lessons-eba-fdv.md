# FFI EBA FDV Foundation

Load this reference for FFI FDV work in the EBA application, including Workspace setup, the 3D building explorer, foundation-table changes, and later migration from the existing Kjeller prototype.

## Source-of-truth boundary

The existing Kjeller map prototype is coupled to Global `u_bygg` and `u_rom_nummer` records and to the earlier EBA floor/layout/desk/booking tables. Treat that model as a prototype integration surface, not as the canonical FDV domain model.

The FDV source of truth belongs in the existing EBA scope and uses the `fdv_` namespace. Do not repurpose or delete the prototype tables as part of ordinary FDV work. Migrate or adapt them only through a separately approved, reconciled change so the current frontend is not broken.

Keep the FDV tables package-private while the Workspace, data resources, and custom components are all in EBA. If a consumer must live in another scope, design and validate the cross-scope/application-access contract explicitly instead of broadly opening every table.

## Foundation model

The MVP foundation consists of six EBA tables:

| Table | Purpose | Parent/reference |
|---|---|---|
| `x_1122545_eba_fdv_location` | Site or campus | — |
| `x_1122545_eba_fdv_building` | Building | mandatory location |
| `x_1122545_eba_fdv_floor` | Storey/floor | mandatory building |
| `x_1122545_eba_fdv_room` | Space/room | mandatory floor |
| `x_1122545_eba_fdv_asset_type` | Reusable technical-equipment classification | — |
| `x_1122545_eba_fdv_asset` | Installed technical asset | mandatory type and building; optional floor and room |

Each hierarchy/classification table has a unique stable code, a mandatory display name, an active flag, and a description. Technical assets use a unique asset ID and also carry status, criticality, manufacturer, model, serial number, responsible group, and placement references.

Use stable codes/asset IDs for integrations and reconciliation. Use `sys_id` only for live references and client state; never encode display labels as reference values. When adding placement validation, enforce that an asset's selected floor belongs to its building and that its room belongs to its floor.

The initial choice sets are deliberately small:

- Room types: office, meeting room, laboratory, workshop, technical room, storage, common area, other.
- Asset categories: HVAC, electrical, plumbing, fire safety, building systems, ICT, furniture, other.
- Asset statuses: planned, in service, out of service, inactive.
- Criticality: 1 critical through 4 low.

Refine these values with FFI before treating them as controlled enterprise taxonomies.

## MVP boundary

The foundation deliberately excludes maintenance plans, work orders, service history, contracts, warranties, lifecycle events, dashboards, and Platform Analytics artifacts. Add those as later domain increments after the location/asset model and user workflows have been exercised. Avoid creating empty lifecycle tables merely to anticipate the full product.

Keep foundation configuration separate from operational data. Do not transport locations, buildings, rooms, or assets in an update set. Use an approved import/seed process with deterministic business keys and reconciliation when sample or real data is requested.

Before seeding, read the live `sys_choice.value` entries instead of deriving internal values from their labels. In the current foundation schema, examples include room type `technical` and asset category `building`; label-like guesses such as `technical_room` or `building_systems` are invalid. An FDV seed should be idempotent by `u_code`/`u_asset_id`, resolve parent records to live `sys_id` values, avoid overwriting existing matches, and reconcile exact counts, duplicate keys, empty mandatory references, and asset building/floor/room consistency after insertion.

When replacing an FDV building that already has dependent floors or assets, inspect every live incoming reference and its `reference_cascade_rule` before deleting the parent. A blank/default rule on a mandatory reference is not a safe cleanup plan because the platform can leave invalid child data. Prefer re-parenting coherent child hierarchies to a resolved replacement building; updating each floor preserves its rooms, while direct asset references must be updated separately. Delete dependent rows only when that additional destructive scope is explicitly authorized, then reconcile zero orphan floors, rooms, and assets plus asset floor/room placement consistency.

## Access model

Use the existing EBA role hierarchy:

- `x_1122545_eba.user`: read FDV foundation records.
- `x_1122545_eba.fdv_manager`: contains the user role; create and update foundation records.
- `x_1122545_eba.admin`: contains the manager role; retains delete and application administration access.

Generated table ACLs retain the EBA admin role. Add the user role only to read and the manager role only to create/write. Validate the exact ACL-role links after transport; do not rely on platform-admin bypass as proof that Workspace users can operate the model.

## Workspace and 3D component readiness

Every table exposed during Workspace creation needs a usable Default form view with its important fields and references. Confirm the form sections and elements are captured in the EBA delivery vehicle; ServiceNow can record `sys_ui_element` update XML as Global even when the section belongs to EBA, so reconcile the update-set application before handoff.

Build Workspace navigation and record pages around the canonical hierarchy. The Three.js component should receive bounded, server-authorized data through UI Builder properties/data resources, emit selection/navigation events, and use record `sys_id` values to open the standard Workspace record route or tab. Keep rendering state separate from record ownership so the 3D scene can evolve without changing the FDV schema.

Before creating the Workspace, re-query the live scope and tables, confirm the six Default views are present, and select these tables in the Workspace table step. Do not create duplicate tables if the picker appears stale; refresh the authoring session and verify scope/application context first.

UI Builder can retain the scoped update-set context that was active when its browser session loaded. After switching `sys_update_set` and `updateSetForScope<scope_sys_id>`, reload or reopen UI Builder, save one small intended artifact, and confirm its `sys_update_xml.update_set` before continuing. If the first artifact lands in the previous set, stop and reopen the authoring session; do not assume the current preference records prove the builder is using them.

Long metadata passes can also overlap another active EBA development session that changes the same scoped update-set preferences. Recheck the preferences during and after the pass, then reconcile capture by the exact expected customer-update natural names—for example `sys_dictionary_<table>_<element>`, `sys_documentation_<table>_<element>_<language>`, and `sys_choice_<table>_<element>`—instead of moving every update created during the time window. Dedupe only between the known source and target sets, and leave concurrent artifacts such as unrelated cross-scope privileges or UI Builder changes untouched. Operational FDV records must remain outside both update sets.

Workspace side navigation and the workspace homepage are separate settings. `chrome_toolbar` controls the visible navigation entries and their order, while `sys_ux_app_config.landing_path` controls the route opened from the workspace root. Verify both when promoting an FDV page to the homepage; placing the route first in side navigation does not change a remaining `landing_path=home`.

## Native building-explorer implementation lessons

The first EBA building-explorer slice, `x-1122545-fdv-building-explorer`, confirmed that the native boundary is viable: a CLI `@servicenow/ui-core` component can receive the six scoped FDV collections through UI Builder properties, normalize the hierarchy, render an accessible HTML navigator/details/assets view, drive an imperative core-Three.js campus scene, and emit a small record-navigation event. React, ReactDOM, React Three Fiber, Drei, a second shell, an iframe, and a custom data endpoint are not required for this MVP boundary.

Use this responsibility split:

| Concern | Owner |
| --- | --- |
| ACL-authorized bounded record reads | UI Builder standard data resources and server ACLs |
| Property/result normalization and hierarchy validation | custom component data modules |
| Selection state shared by HTML and WebGL | custom component state/actions |
| Scene, picking, bounded camera, renderer cleanup | imperative Three.js controller |
| Record route/tab navigation | UI Builder event mapping / Link to destination |

Six bounded standard record-query resources—one for each FDV foundation table—were sufficient for the demonstrated hierarchy. Keep this as the first implementation choice. A page can bind more than one collection to one component; that alone is not material insufficiency that justifies a data broker or Scripted REST resource. Request only the fields used by the component, including stable `u_code`/`u_asset_id` values, relationship identity, safe display fields, internal choice values, and the resolved `sys_id` needed for references/navigation.

UI Builder property fields initially show defaults such as `[]`; component deployment does not create or bind the data resources. Configure and test each real resource, then bind its output. Depending on the resource and formula path, the runtime value may be a direct array, JSON text, or a wrapper such as `result`/`records`. Normalize those supported shapes at the component boundary and keep ServiceNow output-shape logic out of mesh creation.

Normalization must fail safely and retain diagnostics for:

- missing arrays and blank required keys;
- duplicate location/building/floor/room codes or asset IDs;
- floors whose building key is absent and rooms whose floor key is absent;
- assets whose building/floor/room placement disagrees with the resolved hierarchy;
- missing live reference `sys_id` values;
- unknown internal status, criticality, room-type, or asset-type values.

Render usable partial data and an accessible validation summary where possible. Do not invent display behavior by guessing a choice label; preserve the actual internal value and provide a restrained unknown-state treatment. Never hard-code the current PDI's record sys_ids in source.

For Norwegian client-side search over already bounded UI Builder data, keep display values unchanged and normalize only the comparison index. Lowercase with a Norwegian locale, apply Unicode NFD and remove combining marks, then transliterate `ø` to `o` and `æ` to `ae` explicitly. NFD does not decompose `ø` or `æ`, so accent stripping alone makes a query such as `moterom` miss `Møterom`. Test both native and transliterated spellings, keep the minimum query length bounded, and resolve every hit back through the existing stable-key selection path instead of creating a second navigation state.

### Renderer and cache findings

After every component source/manifest deployment or page-binding/event change, read back the deployed component metadata and use UI Builder's hamburger menu **Developer > Clear UI Builder cache** before judging the result. Reopen UI Builder after the cache action and test the real EBA route in a fresh tab. The authoring cache proved capable of showing stale/blank output after a successful normal deployment. Recreating the page is not the preferred repair because it can discard valid data-resource and event mappings while masking the stale layer.

For a custom component to occupy the remaining Workspace viewport height, make the height contract explicit at both boundaries: set the UI Builder page/container layout to `height: 100%`, then propagate `height: 100%` and `min-height: 0` through the custom-element host and its internal shell. Use a flexible content track such as `minmax(0, 1fr)`, remove fixed `max-height` caps from independently scrolling side panels, and verify the rendered host, main layout, and document bottom numerically at the target viewport. If the internal grid includes an optional status/banner row that becomes `display: none`, do not rely on auto-placement for the main layout; assign it to the intended flexible grid row (or change the template) so the hidden child cannot shift content upward and leave an unused track at the bottom.

For wide three-panel explorer layouts, express the desktop emphasis with proportional `minmax()` tracks while retaining a readable minimum for each side rail. Verify the computed pixel widths and percentages at both a normal desktop viewport and the user's target large viewport; fraction values alone can be misleading once minimums and breakpoints participate. Keep side rails independently scrollable, and preserve separate two-column/mobile breakpoint rules instead of forcing the wide-screen proportions into narrower layouts.

During the Australia PDI investigation, repeated dynamic `data-*` attributes used as delegated event plumbing coincided with the component rendering white. A minimal semantic view and then a simple data-driven building list rendered after those attributes were removed. Treat this as a target-version observation: use ui-core renderer actions and closures (`on-click={() => dispatch(...)}`) for native HTML controls, and introduce any custom dataset/hook/ref one at a time in the deployed runtime.

Do not use a guessed top-level `onConnect` signature to locate the Three.js mount through nested shadow roots. The installed ui-core renderer contract did not match that assumption and the result was a request-animation-frame loop that never reached a usable mount. Keep a stable mount element in the component view; synchronize/create the scene from a verified render lifecycle action such as `SEISMIC_COMPONENT_RENDERED`; tear it down from the matching disconnect action; and inspect the installed package source/types before using a lifecycle API copied from older examples.

The Three.js controller should be stored once per component host/root, commonly via `WeakMap`. Bound the device-pixel ratio, use `ResizeObserver`, pause or render on demand when not visible, respect reduced motion, keep plan/isometric/reset/zoom controls recoverable, and dispose every geometry, material, texture, render target, renderer resource, observer, DOM listener, pointer handler, pending frame, cursor, and transient hover state. When a floor or room becomes selected, derive the owning building code for scene emphasis rather than assuming every selection has a building-shaped record.

A WebGL canvas rendered near `1x` device-pixel ratio can look visibly softer than adjacent vector DOM text on a large display, even when its CSS dimensions are correct. For a demand-rendered scene, prefer adaptive supersampling with a useful desktop floor, a device-ratio ceiling, and a total drawing-buffer pixel budget; render canvas-backed label textures at a higher source resolution while preserving their logical scene size. Verify `canvas.width / canvas.clientWidth` and `canvas.height / canvas.clientHeight` numerically at the target viewport instead of judging a screenshot alone.

Detached triangles or a straight cut through the far edge of an otherwise valid campus scene can be camera clipping rather than malformed footprint triangulation. For an orthographic isometric camera, size the far plane beyond the camera-to-target distance plus the radius of the largest rendered context layer, with explicit margin, and test the bound across the full supported yaw range. Keep the camera, ground dimensions, and clipping distance in one shared scene contract so later geometry expansion cannot silently reintroduce the slice.

Avoid scaling a hovered or selected mesh when its geometry vertices are authored directly in campus/world coordinates: Three.js scales around the object's local origin, so a seemingly small interaction scale can visibly translate a building whose footprint is far from that origin. Prefer stationary interaction feedback through material color, emissive treatment, outline visibility, and label emphasis. If scale is deliberate, first center the geometry around a local pivot and position the object separately, then test that its world-space centroid remains fixed.

For a dense facility hierarchy, keep descendant visibility as component-owned transient state instead of rendering every floor and room open by default. Use a distinct native disclosure button beside the record-selection button: the disclosure control owns `aria-expanded` and a descriptive expand/collapse name, while the record button owns selection and navigation intent. This separation prevents branch exploration from unexpectedly changing the selected record, preserves native Enter/Space behavior, and avoids fragile delegated `data-*` interaction plumbing. Keep buildings visible initially, reveal floors and rooms one level at a time, and ensure collapsing a branch does not mutate the current record selection.

### Campus geometry and operational seed findings

When adapting a separate React/Three.js campus prototype into a native UI Builder component, reuse only portable scene facts such as footprint coordinates, colors, paths, and Three.js math. Do not transplant React, ReactDOM, React Three Fiber, Drei, router/session code, or the prototype shell. Remap every prototype geometry key explicitly to the scoped FDV building natural key; do not rely on array order, display labels, or a fallback grid for live records.

Connected physical complexes may need separate schematic sub-footprints so each operational building record remains independently selectable. Keep small unlabeled/context footprints visual-only and out of the raycast target set. Treat a user-supplied aerial/site image as calibration evidence unless redistribution was explicitly authorized; do not bundle it as an application asset by default. Record in the component contract which footprints are schematic and which heights are illustrative.

Do not render ground-level pedestrian paths with `TubeGeometry`. Its radial faces, raised silhouette, and directional shading make even narrow centerlines read as pipes or curbed vehicle roads. Sample the centerline into a flat indexed ribbon instead, add only a slightly wider and darker flat underlay for edge separation, use rounded planar end caps, keep both layers just above the landscape to avoid z-fighting, and disable cast shadows. Classify widths as primary paths, secondary links, and paved plazas, then validate them in plan and isometric views against aerial context without bundling the reference imagery.

When a user marks missing campus paths on a rendered plan screenshot, calibrate the screenshot back to the scene grid with several known building-edge anchors before tracing coordinates. Decompose the strokes into named centerlines at real junctions, snap endpoints to existing path nodes, plazas, or building edges, and keep intermediate bends schematic. Stable path IDs plus a topology test are more maintainable than one long anonymous polyline and make later corrections local without implying that the annotation is surveyed or suitable for navigation.

Size the UI Builder building query above the reconciled live building count but keep it deliberately bounded. In the FFI campus slice, the page limit was raised from 10 to 25 for 19 live demo records, while only the 16 numbered physical campus records received geometry. Preserve older/legacy operational records in the hierarchy unless deletion was explicitly authorized.

### Record navigation and page metadata

The component's open-record event contract is properties/events out, for example `{table, sysId, source}` where `source` identifies the building explorer. The manifest action deploys as component event metadata; the component dispatches the resolved live record identity; UI Builder maps it to the standard EBA record route. Keep workspace path, page definition, route metadata identifiers, and instance sys_ids out of source.

When a details panel lists child records such as technical assets, reuse that same open-record event instead of adding one event or navigation implementation per record type. Normalize every child with its live `table` and `sysId`, render its identity as a native accessible button, dispatch the child record through the existing payload builder, and let the page's single record-route relay open the Workspace tab. Verify the data resource explicitly returns `sys_id`, the rendered control is not disabled by a rejected identity, the child-record payload test passes, and the live relay binds both `table` and `sysId`. When a live click remains silent, add temporary bounded client diagnostics at the click request, identity validation, and framework dispatch boundary without logging full records or sys_ids: no request log isolates the renderer/control, a rejection isolates normalization or data, and a completed dispatch isolates the remaining fault to the page relay or Workspace shell. A CLI deployment can leave a component event with a valid `event_name` and payload schema but an empty `label`; give every component event a descriptive label so UI Builder exposes the source event clearly. Do not assume null `sourceEventSysId` or `sourceEventDefinition.id` is malformed: Australia commonly stores component mappings by `sourceEventApiName` with those IDs null. Validate the complete chain instead: the component macroponent lists the dispatched `sys_ux_event`; its API name matches the framework dispatch; the page definition's component `eventMappings` targets a scoped relay and binds the payload; and the active page variant's `sys_ux_screen.event_mappings` maps that relay to the inherited shell event such as `sn_canvas_core.NAV_ITEM_SELECTED`. A relay displayed under page-level **Dispatched events** is only an exposed source; when the variant row is `[]` or the UI shows only **Add handler**, navigation stops at that relay. If UI Builder reports a relay as missing even though a hand-created `sys_ux_event` row is visible through the Table API, do not treat row existence as runtime acceptance: prefer recreating the handler in UI Builder or reusing a proven Workspace Builder-generated scoped route relay, and align the relay API name, target event `apiName`/`sysId`, page definition `dispatched_events`, and active screen's variant mapping. A separate asset-specific event adds contract and page-mapping drift without improving navigation.

Configure event mapping in UI Builder where practical. Direct JSON editing of `sys_ux_macroponent.composition` is release-sensitive and was proven hazardous: a PowerShell conversion unwrapped the one-element top-level array into an object, producing **No URL and/or Screen** in UI Builder and **No content available** at runtime. If a narrowly approved automation is unavoidable, retain the before-value, preserve the top-level and nested arrays explicitly, assert the serialized value begins with `[`, reread/parse it, verify its update set, clear UI Builder cache, and then validate both editor and Workspace.

When UI Builder reports that a page references a missing `sys_ux_event`, resolve the event mapping's target `apiName` and owning page scope before repairing it. A valid replacement relay can already exist under that same event name while the composition retains only an obsolete `sysId`. Prefer removing and recreating the handler in the UI Builder Events surface. If that surface is unavailable and a narrow metadata repair is approved, replace only the single stale target ID, verify the resolved event name/scope/property contract, preserve component, mapping, target, and top-level array counts, reread the exact composition, and confirm natural update-set capture.

Treat the literal missing-event ID `undefined` as a distinct UI Builder save defect. Inspect the component mapping targets: the wizard can append an otherwise shaped `{type: "EVENT"}` target whose `event` value is `null`, while leaving the earlier valid relay target intact. That null target renders as **This handler is not valid** and triggers the `sys_ux_event` ID `undefined` error; it is not evidence that an actual event row with that ID was deleted. Remove only the invalid inner handler card (or, with narrow approval, only the null target), preserve the valid relay, and then complete the relay-to-shell handler in the active screen's `sys_ux_screen.event_mappings` rather than repeatedly adding component handlers.

Before any UI Builder save, confirm EBA scope and the intended in-progress EBA update set. Reopen the builder after preference changes, save one small artifact, and verify `sys_update_xml.update_set`. The six data resources, page bindings, relay mapping, and page composition are application metadata; the FDV location/building/floor/room/type/asset rows remain operational data and do not belong in the update set.

### Dense Details-panel presentation

When a wide FDV Details rail combines facility attributes, summary counts, and several heterogeneous lifecycle record types, do not leave the content as one continuous white text surface and do not force every record type into one literal HTML table. Present homogeneous key/value attributes in a responsive `dl` grid with thin internal row and column dividers so it reads like a table, while keeping the surrounding surface white and visually light. Present work orders, plans, contracts, documents, suppliers, systems, and assets as native-button list rows separated by dividers inside their owning section. This preserves wrapping, badges, descriptions, and accessible record actions while making section and row boundaries visible without decorative shadows.

Limit large-screen attribute grids to a deliberate column count and reduce them to two and then one column at narrow breakpoints. Prefer one-pixel theme-token dividers and unfilled headings before adding rounded containers, tinted card backgrounds, or stronger enclosing borders; use a thin section outline only where a long heterogeneous record list needs ownership. Validate the component at the user's actual wide viewport because a technically present low-contrast divider can disappear perceptually when large amounts of whitespace separate related fields. This is a presentation-only change: retain existing UI Builder data resources, property bindings, and event mappings unless runtime evidence identifies a data or navigation defect.

Do not assume a CSS-variable fallback will make an imperceptible host divider visible: the fallback is ignored whenever the host defines the variable, even if that defined color is too faint for the actual wide layout. When rendered evidence shows this failure, define one component-scoped neutral grid-line token with restrained but explicit contrast, use it consistently for the section frame, header rule, and one-pixel CSS-grid gaps, and keep cell backgrounds on the active theme surface. Grid gaps avoid breakpoint-specific `nth-child` border bookkeeping while preserving a real line between every populated cell.

Apply the same caution to UI Builder background tokens in dense data grids. A host can legitimately resolve its nominal primary background to a tinted blue-grey, turning every key/value cell into one heavy filled block even when the component's structure and borders are correct. For a deliberately light Details rail, define a small component-owned surface palette: one quiet canvas tone, explicit white data cells, one subtle header tone, one neutral divider, and one restrained accent for section ownership and interactive states. Keep these tokens local to the component, verify the minified live asset contains them after deployment, and judge the hierarchy from a rendered wide-screen view; source-level fallbacks and successful compilation do not prove the host theme will produce the intended contrast.

### Validation and rollback guardrails

Keep the foundation smoke-test component `x-1122545-fdv-foundation-card` deployed until the real explorer is accepted. It distinguishes toolbox/page/cache failures from explorer bundle failures and provides a quick rollback comparison. A safe incremental deployed test is: static heading -> normalized building count/list -> full hierarchy -> synchronized selection/details -> stable Three.js mount/geometry -> camera/pointer behavior -> asset panel -> open-record event.

Local tests should cover manifest/tag/action consistency, missing arrays, duplicate natural keys, invalid parent references, asset placement inconsistency, unknown choices, selection transitions, event payloads, empty states, and lifecycle source invariants. Production build and normal CLI deployment without `--force` are necessary but insufficient. Runtime acceptance still requires real scoped data, mouse and keyboard selection, HTML/WebGL synchronization, plan/isometric/reset/zoom behavior, loading/empty/error/WebGL fallback, open-record routing, console cleanliness, remount cleanup, desktop/narrow layouts, and the intended EBA persona rather than administrator alone.

Rollback removes the new component instance/event mapping/data-resource bindings from the page or redeploys the previous component source revision. It does not delete the page, foundation smoke component, or operational FDV records.

## FDV handover archive to MVP lifecycle model

An FDV handover archive organized by NS 3451 disciplines typically mixes reusable product data, asset-specific commissioning evidence, supplier/contact registers, room and equipment schedules, as-built drawings, maintenance instructions, and multi-system test protocols. Do not treat every file as an asset or upload the archive as an unstructured attachment pile.

For the first lifecycle increment, use these boundaries:

- Keep one governed FDV document register with document type, revision/date, discipline/classification, supplier, and optional references to building, floor, room, asset type, or asset. Attach the file to that record. Relate reusable manuals to the asset type and asset-specific certificates or tests to the installed asset or physical context.
- Capture recurring interval, next due date, responsible group/supplier, instructions, required competence or safety note, and expected duration on the maintenance plan. Generate a custom work order from the plan; do not create a separate runtime table merely to duplicate a scheduled occurrence.
- Treat completed custom work orders, their close notes, work notes, dates, and evidence attachments as the service and maintenance history. Add a separate history table only when a later requirement needs immutable structured event types that work orders cannot represent.
- Carry external identity where it has an integration use: an NS 3451 or system classification on the asset type, a TFM/plant tag on the installed asset, and an optional IFC/BIM GUID on physical records used by the 3D model. Keep the existing natural `u_code`/`u_asset_id` as the stable ServiceNow reconciliation keys.
- Prefer a parent-asset self-reference for simple equipment/system decomposition. Introduce a relationship table only when one asset genuinely needs multiple typed relationships.

Do not assume that the presence of an architectural or federated IFC proves complete room geometry. A discipline export can contain far fewer `IfcSpace` objects than the authoritative room schedule. Reconcile storey and room counts, room numbers, and natural keys across the room schedule, as-built plans, and IFC before enabling spatial navigation. Keep the complete operational room register in ServiceNow, keep view geometry in a separate adapter keyed by the stable room code or number, and label partial or manually derived layouts as schematic. Never manufacture room dimensions from area alone. This separation lets a later corrected IFC or GLB export replace the geometry without rewriting the lifecycle records.

When a floor explorer must cover records that have no authorized interior geometry, make provenance a rendered part of the layout contract rather than an implementation note. Keep source-derived adapters keyed by stable floor codes. A register-only fallback may use deterministic equal-weight cells for selection only when it is visibly and accessibly labeled non-spatial and not measured, ignores area and capacity when calculating geometry, and explicitly disclaims actual size, shape, adjacency, orientation, and access. Test room-key parity, coordinate bounds, area-independence, and replacement of one floor adapter at a time. For sensitive facilities, do not search for, infer, or reconstruct missing interiors from public imagery or operational clues.

For a room-by-room showcase seed, validate one room as a complete vertical slice before scaling: resolved room -> existing or new asset -> maintenance plan -> Task-derived work order. Reuse a credible existing room asset instead of inserting a second asset solely for symmetry, and keep shared building documents or contract coverage at building scope rather than duplicating identical rows for every room. On the full pass, reconcile that every target room has at least one asset and exactly the intended plan/work-order count, all asset/building/floor/room references agree, completed orders are inactive while open states remain active, deterministic keys are unique, and a second run creates zero records. This produces rich Details-panel data without N-times duplication or broken placement chains.

When the Details panel drills down to a room, separate navigation context from lifecycle match eligibility. Retain the parent floor and building in the resolved scope for breadcrumbs and orientation, but do not let those parent identifiers match general documents, plans, work orders, contract coverage, or systems. At room scope, match only the room itself, equipment placed in that room, asset types represented by that equipment, and records reached through an already matched plan or contract. Building and floor selections can retain their broader inheritance behavior. Regression tests should pair one applicable room/equipment record with one building-only record for every lifecycle collection so a future refactor cannot silently restore parent inheritance.

For an operational room overview, derive attention from current condition and work—not from room type or asset criticality alone. Use a small explicit precedence such as: urgent for out-of-service equipment, overdue activity, open priority-1 work, or a waiting/blocking state; follow-up for new or in-progress work; planned for planned work/equipment or maintenance due soon; healthy otherwise. Scope the calculation to records explicitly linked to the room or to an asset placed in that room. Do not reuse the broader Details-panel inheritance rule for this purpose, because a building-level record would then color every descendant room. Keep selected/focused state visually separate from operational severity, pair every color with a persistent text label and summary count, and test the rule with a fixed date plus the date formats returned by the target UI Builder resource.

When the custom FDV work order extends `task`, align its state values with `TaskStateUtil` instead of only relabeling inherited numeric values. The demonstrated MVP mapping uses New `1`, Planned `-5`, In progress `2`, Waiting `5`, Completed `3`, and Cancelled `7`, with a state Dictionary Override containing `close_states=3;7,default_work_state=2,default_close_state=3`. Without that override, Task business rules treat values `3`, `4`, and `7` as inactive, can close records labeled In progress or Waiting, and can rewrite a nominal Completed state. Verify both `state` and `active`/`closed_at` through a real insert and update. For idempotent demo work-order seeds, coalesce on the stable external reference and treat `work_notes` and `close_notes` as create-only journal inputs so reruns do not append duplicate entries.

Do not filter an FDV work-order UI Builder resource with inherited `active=true` when the component also presents service history. A correctly completed Task-derived work order has `active=false`, so that filter silently removes the very records that prove completed maintenance. Use a bounded state allowlist such as `stateIN-5,1,2,3,5,7` (or another deliberate history window), request both `state` and `active`, and reconcile the returned count and state distribution against live demo records. In the demonstrated lifecycle slice, `active=true` returned three orders while the state allowlist returned all four, including the one Completed record.

Treat an FDV system as a governed functional grouping, not as another asset type or an inference from NS 3451. Bind `asset.u_system` by the system record `sys_id`, retrieve the bounded system collection separately, and resolve Details scope from the explicit system building plus the selected assets' system references. When `system.u_building` is optional, a system without that reference is campus-wide: include it at location scope, but do not silently apply it to every building, floor, or room unless an in-scope asset explicitly references it. Preserve and report an invalid non-empty building reference instead of misclassifying that system as campus-wide.

A new `u_footprint_geojson` field is not sufficient evidence to replace established campus geometry. In the demonstrated PDI the field was an 8,000-character string and no building record populated it, so there was no live evidence for coordinate reference, axis order, ring closure, or the transform into the component's campus-local grid. Validate populated input as bounded Polygon/MultiPolygon JSON, retain the known schematic footprint on missing or invalid input, and show a safe partial-data issue rather than feeding unverified coordinates to Three.js. A positive decimal `u_height_m` is different: it is already in the scene's metre unit and can safely override the schematic height while missing values retain the fallback. Promote GeoJSON to rendered geometry only after representative records prove the CRS/projection and visual alignment.

This model keeps the operational core small while preserving traceability from physical place and equipment through plans, work execution, suppliers/contracts, and the documentary evidence received at handover.

### Norwegian-only scoped labels

For a Norwegian-only scoped FDV app, localize the base labels while preserving every technical table name, element name, choice value, API name, and relationship. Update the custom tables' labels/plurals, their `sys_dictionary.column_label` values, the corresponding base-language `sys_documentation` rows, and all scoped `sys_choice` labels. For fields inherited from Task, create table-specific `sys_documentation` rows and table-specific choices on the custom work-order table; never alter global Task labels or choice records. Localize both runtime component copy and UI Builder authoring metadata, including manifest property labels, component/action labels, page-instance heading values, and the composition-stored `elementLabel`. Changing a component default does not override a literal already stored in page composition. Run the post-deployment label step after the normal component deployment, because CLI deployment may rewrite component event metadata, then prove idempotence with a second zero-change run and verify update-set capture in the intended scope.

### Default list-layout parity

For backend and Configurable Workspace list parity, maintain one global `Default view` list layout per canonical FDV table and make Workspace `sys_ux_list.view` point explicitly to the platform Default view while leaving `sys_ux_list.columns` empty. A Workspace list with its own columns becomes a second source of truth. Inspect user-specific `sys_ui_list` parents as well: a personal layout overrides the global Default and must be deliberately reset when uniform presentation is the requirement. ServiceNow can store list columns as modern `sys_ui_list` parent plus `sys_ui_list_element` children or as direct element rows on `sys_ui_list`; preserve a working representation unless normalization is required. `List Element` customer updates can be captured with `application=global` even when their parent list layout belongs to EBA, so reconcile only the exact intended update-set rows to the EBA application and verify any removed columns have explicit `DELETE` captures before handoff.

### Native related lists for FDV references

When an FDV child table already has a direct dictionary reference to its parent, expose the inverse relationship with a Default-view `sys_ui_related_list` and a `sys_ui_related_list_entry.related_list` value in the form `<child_table>.<reference_field>`. For example, the room form's work-order list is `x_1122545_eba_fdv_work_order.u_room`. Do not create a `sys_relationship` record for that ordinary one-to-many case; reserve defined relationships for calculated, filtered, or otherwise non-dictionary relationships. Keep completed work orders visible unless the business requirement explicitly asks for an active-only view, and use the entry's `order_by` field for a useful natural sort. Related-list entry customer updates can inherit `application=global`; reconcile only the exact entries created in the intended EBA update set, then verify the related-list parent/entry count, exact relation strings, representative child query results, and Workspace rendering on the record page.

### Task-derived work-order forms and activity

For a custom FDV work order that extends `task`, reuse the inherited assignment, journal, audit, attachment, and related-list capabilities instead of building a parallel activity implementation. The EBA `Record Default` page already contains native Activity Stream Compose and Activity Stream components. Keep `watch_list`, `work_notes`, and `comments` on the Workspace form view so those components have the expected Task journal fields, but do not add a second `activity.xml` formatter to that Workspace view. On the backend Default form, include `activity.xml` with `type=formatter` together with the journal fields so the standard form renders the familiar activity stream.

Model structured forms with `sys_ui_form`, ordered `sys_ui_form_section` links, `sys_ui_section`, and `sys_ui_element` rather than appending every field to one legacy section. On upgraded instances, an old Default section may store the literal view value `Default view`, while the modern form points to the actual Default `sys_ui_view.sys_id`; treat them as distinct layouts and validate which one the runtime uses before modifying or removing either. Reuse section-local split markers first because `.begin_split`, `.split`, and `.end_split` repeat across sections; matching them globally makes an otherwise idempotent installer rotate metadata on every run. After configuration, prove a second run reports zero creates and zero changes, verify every form and section belongs to the intended application scope/package, and read back the exact activity elements for both views.

An App Engine-generated Workspace can select one experience-wide form view through the root `sys_ux_page_property` whose `name=view`; in the EBA Workspace this originally pointed to the generated `workspace-<path>-<n>` view. To consolidate backend and Workspace onto OOTB `default`, first inventory every table with sections in the generated view and require a usable Default section for each. Then inspect direct references from Workspace View Rules, UX lists, action layouts, UI policies, and declarative-action assignments; switch the root property to `default` before removing the generated view. A `sys_ui_view` deletion cascades to its owned `sys_ui_form`, `sys_ui_section`, and `sys_ui_list` metadata, so count that scope up front, retain update-set rollback evidence, and verify the exact UI View, Form Layout, and List Layout `DELETE` captures. Finally require a zero-change rerun and prove the generated view and its dependent form/list rows are absent while the canonical Default form remains intact.

### Scripted maintenance MVP delivery lessons

In an Australia-family scoped app, do not use `gs.nowDateTime()` for stored timestamps: script fencing can reject it even when the same code works in Global. Use `new GlideDateTime().getValue()` for date/time fields and `new GlideDate().getValue()` for date fields, then execute the real Script Include in the target scope rather than relying only on static source tests.

Scoped server verification can create cross-scope privilege records merely by exercising test-only cleanup, attachment-writing, impersonation setup, or global user tables. After a self-cleaning test, audit both `sys_scope_privilege` and the intended update set. Keep only privileges required by production code—such as event queuing or read access to `sys_attachment` for evidence validation—and remove exact test-only privilege records plus their customer updates before handoff.

The repository deployment runbook intentionally rejects any update set whose summary reports possible noise, including legitimate but review-sensitive changes to existing form layouts or cross-scope privileges. Keep the custom maintenance backend in its manually audited EBA update set and deploy the Git-managed UI component through a separate clean EBA update set when that boundary is needed. Never bypass the audit with force; leave both update sets in progress unless the user explicitly requests completion/export.

For bounded operational assignment changes on package-private EBA tables, do not treat a Global Xplore loop as successful merely because the script completes or reports the attempted sys_ids. Check every `update()` return value and re-read the exact reference field; a cross-scope attempt can fail to persist without proving the intended data state. Prefer the authenticated Table API for ordinary work-order and maintenance-plan reference updates when its ACL path is available, and verify each response plus a final aggregate reconciliation. Maintenance-plan updates still execute the scoped validation Business Rule: if a legacy plan lacks every schedule anchor/date, leave it unchanged and report the data-quality blocker rather than using `setWorkflow(false)`, inventing a date, or otherwise bypassing validation.

On Task-derived scoped tables, a successful collection query does not guarantee that the corresponding direct-record Table API GET or PATCH will behave consistently; an intermittent `No Record found` response is not proof that the child or parent record is absent. Cross-check the exact child-table collection row and its Task parent before drawing an ACL or inheritance conclusion. For an explicitly authorized operational change, resolve each target by a stable task number with an exact, unique child-table query; if direct-record access remains unreliable, use a bounded GlideRecord update in the owning application scope, require the expected active/group/assignee preconditions, reject non-unique matches, require a non-empty `update()` result, and immediately re-read every changed field. Finish with an aggregate reconciliation using the same dynamic filters the dashboard runs as the target user.
